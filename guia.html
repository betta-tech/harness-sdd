harness-sdd — Guía de Harness Engineering

Arnés de desarrollo multi-agente en Python. Demuestra cómo estructurar un repositorio para que agentes de IA (leader, spec_author, implementer, reviewer) trabajen de forma autónoma, colaborativa y verificable bajo el estándar Spec Driven Development (Kiro-style).

📜 1. Filosofía: El Repositorio ES el Sistema

En el desarrollo tradicional asistido por IA, el contexto fluye por la ventana de chat: es volátil, sufre de pérdida de atención ("efecto teléfono descompuesto") y se borra al cerrar la sesión.

Harness Engineering invierte la premisa: el contexto no circula por chat, vive en disco y queda versionado en Git.

❌ Modelo Volátil (Chat)
  • El humano repite requisitos una y otra vez.
  • El agente olvida decisiones pasadas tras varias vueltas.
  • No hay evidencia ejecutable de si el cambio respeta la arquitectura.
  • Al cambiar de modelo o sesión, se pierde todo el historial.
✅ Modelo Harness Engineering (Disco)
  • specs/<feature>/ guarda requerimientos inmutables en EARS.
  • progress/current.md refleja la sesión viva al instante.
  • feature_list.json define el alcance exacto y estado de cada feature.
  • CHECKPOINTS.md y init.sh evalúan objetivamente el estado final.
💡 La Aplicación Notes CLI es el Vehículo Didáctico
El código de notas en Python (src/storage.py, notes.py, cli.py) es deliberadamente simple para que cualquier desarrollador o auditor pueda comprenderlo de un vistazo. Lo valioso no es qué hace el programa, sino cómo está arnesado para que la IA nunca se desvíe.

👥 2. El Equipo Multi-Agente (.claude/agents/)

El arnés divide las responsabilidades en 4 subagentes especializados. Ningún agente tiene permiso para hacer el trabajo de otro:

Orquestador
leader
Recibe la tarea del usuario, revisa feature_list.json y lanza los subagentes adecuados.
Regla dura: NUNCA escribe código ni tests. Se detiene ante la puerta humana.
Analista / Diseñador
spec_author
Toma una feature pending y redacta la triada en specs/<name>/.
Regla dura: Solo cambia status a spec_ready y PARA. No toca src/.
Artesano / Builder
implementer
Toma una feature in_progress ya aprobada y ejecuta las tareas de tasks.md una a una.
Regla dura: Solo trabaja si el spec está aprobado. Escribe test antes de marcar [x].
Auditor de Calidad
reviewer
Audita el código contra docs/, specs/ y CHECKPOINTS.md.
Regla dura: Emite APPROVED o CHANGES_REQUESTED. No edita código.
Subagente Entrada Principal Archivos que Escribe Herramientas Permitidas
leader Prompt de usuario, feature_list.json progress/current.md, progress/history.md, feature_list.json Read, Glob, Grep, Bash, Agent
spec_author feature_list.json (feature pending) specs/<name>/{requirements,design,tasks}.md Read, Write, Edit, Glob, Grep, Bash
implementer specs/<name>/ (aprobado) src/*.py, tests/*.py, progress/impl_<name>.md Read, Write, Edit, Glob, Grep, Bash
reviewer Diff de Git, spec y CHECKPOINTS.md progress/review_<name>.md Read, Glob, Grep, Bash

🔁 3. Flujo Spec-Driven Development (SDD) & Puerta Humana

El flujo SDD impide que la máquina gaste tokens o genere código inútil hasta que el humano certifique que el diseño resuelve el problema deseado.

pending
➔
[spec_author]
➔
spec_ready
➔
⏸ PUERTA HUMANA (Aprobación)
➔
in_progress
➔
[implementer ➔ reviewer]
➔
done
✋ La Puerta de Aprobación Humana es Sagrada
Cuando spec_author finaliza la redacción del spec, la feature pasa a spec_ready y el sistema SE DETIENE OBLIGATORIAMENTE. El humano abre los tres archivos en su editor (VS Code, Cursor, terminal):
  1. Lee specs/<name>/requirements.md para validar el alcance funcional.
  2. Lee specs/<name>/design.md para certificar las decisiones técnicas.
  3. Lee specs/<name>/tasks.md para revisar el plan de tareas paso a paso.
Solo cuando el humano responde en el chat "aprobado", el leader transiciona el estado a in_progress e invoca al implementer.

📐 4. EARS Notation & La Triada de Especificación

Cada feature con "sdd": true cuenta con una carpeta exclusiva en specs/<nombre-feature>/ con tres documentos complementarios:

1. requirements.md — Sintaxis EARS Estricta

Para evitar prosa ambigua, todos los requerimientos funcionales usan los 5 patrones canónicos de EARS (Easy Approach to Requirements Syntax):

Patrón EARS Estructura / Plantilla Ejemplo en Notes CLI
Ubicuo El sistema DEBE <acción>. El sistema DEBE almacenar las notas en formato JSON atómico.
Evento CUANDO <disparador>, el sistema DEBE <acción>. CUANDO el usuario ejecuta recent, el sistema DEBE listar las 5 notas más recientes.
Estado MIENTRAS <estado>, el sistema DEBE <acción>. MIENTRAS no existan notas en el archivo, el comando list DEBE salir con exit code 0 y stdout vacío.
Opcional DONDE <feature opcional>, el sistema DEBE <acción>. DONDE se provee --limit N, el sistema DEBE listar como máximo N notas.
No deseado SI <evento de error> ENTONCES el sistema DEBE <acción>. SI el ID no existe ENTONCES el sistema DEBE imprimir un mensaje en stderr y salir con código != 0.
2. design.md — Decisiones Técnicas
Especifica qué archivos de src/ se modificarán, las firmas de función exactas, nuevos argumentos de argparse, tipos de excepción a capturar y la alternativa técnica descartada justificando por qué no se eligió.
3. tasks.md — Checklist de Implementación
Lista ordenada de pasos discretos [ ] T1, [ ] T2... Cada task indica explícitamente qué requerimientos R<n> cubre. El implementer las va marcando con [x] conforme las completa con sus respectivos tests.

💾 5. Gestión de Estado y Memoria Viva

El repositorio gestiona el estado a través de archivos estructurados:

Archivo Propósito Quién lo Modifica
feature_list.json Registro de todas las features, criterios de aceptación, reglas de negocio y estado global. leader / implementer
progress/current.md Memoria viva de la sesión activa: qué feature se trabaja, plan en curso y bloqueos inmediatos. leader / implementer
progress/history.md Bitácora histórica inmutable (append-only) que resume cada sesión terminada. leader al cerrar sesión
progress/impl_<name>.md Informe del implementador: lista de archivos tocados, mapa de trazabilidad R<n> → test y output de tests. implementer
progress/review_<name>.md Informe de auditoría con veredicto (APPROVED o CHANGES_REQUESTED) y checklist de checkpoints. reviewer

🎯 6. CHECKPOINTS.md — Criterios de Evaluación

"En sistemas multi-agente no se evalúa el camino, se evalúa el destino." Cualquier juez (humano o IA) evalúa la salud del repo con los 6 Checkpoints objetivos:

C1 — Arnés Completo
Existen los 4 archivos base, los 3 docs arquitectónicos y ./init.sh termina con exit code 0.
C2 — Estado Coherente
Como máximo 1 feature en in_progress en feature_list.json. Toda feature done tiene tests verdes.
C3 — Respeto Arquitectónico
src/ solo contiene módulos previstos. Cero dependencias externas. Sin prints de debug ni TODOs huérfanos.
C4 — Verificación Real
Tests usan tempfile.TemporaryDirectory() (cero mocks falsos de fs). 100% de la suite verde.
C5 — Sesión Bien Cerrada
Cero archivos basura sin trackear. Entrada añadida en progress/history.md. current.md limpio.
C6 — SDD Estricto
Feature tiene su carpeta specs/<name>/ con los 3 archivos. EARS verificado. Trazabilidad 100%.

🏛️ 7. Arquitectura del Código Python (3 Capas)

El código de la aplicación se divide estricta y únicamente en tres capas:

Flujo de Datos — src/ 
usuario  ───>  src/cli.py (argparse + presentación en stdout/stderr)
                     │
                     ├──> construye Note con src/notes.py (@dataclass frozen=True)
                     │
                     └──> src/storage.py (load / save atómico con tempfile + replace)
                              │
                              └──> .notes.json (en CWD)
Reglas de Oro del Código Python
  • Python 3.9+ estándar: Sin librerías de terceros en requirements.txt (stdlib pura).
  • Inmutabilidad: La entidad Note es un @dataclass(frozen=True). Modificar significa generar una nueva instancia.
  • Escritura atómica: save() siempre escribe primero en un archivo temporal con tempfile.NamedTemporaryFile y luego hace os.replace() para evitar archivos corruptos ante fallos imprevistos.
  • Excepciones del dominio: NoteError y NoteNotFound en notes.py. El CLI las atrapa, imprime a stderr y sale con código 1.

🛡️ 8. init.sh & Verificación Automatizada

El script ./init.sh es el guardián de la integridad del repositorio. Se ejecuta al iniciar cualquier sesión y antes de declarar cualquier feature terminada:

Terminal — Ejecutar verificación 
./init.sh

Las 5 Fases de init.sh

  1. Entorno: Verifica presencia de python3 y versión compatible (>= 3.9).
  2. Archivos base: Comprueba la existencia de los 4 archivos de gestión y los 3 de documentación.
  3. Consistencia del estado: Valida la sintaxis JSON de feature_list.json y verifica que toda feature con "sdd": true no-pending tenga su carpeta de specs.
  4. Suite de tests: Ejecuta python3 -m unittest discover -s tests -v (actualmente 27 tests).
  5. Resumen: Emite código de salida 0 si todo está [OK] o 1 si existe algún fallo.

🚀 9. Tutorial Práctico: Implementando una Feature con Claude Code

Aprende a trabajar como un líder de ingeniería interactuando con Claude Code en este arnés:

Paso 1: Verificar el Entorno
Ejecuta ./init.sh en la raíz. Si termina en verde, continúa.
Paso 2: Abrir Claude Code
Lanza Claude Code en la terminal de la raíz del repo:
Terminal
claude
Pídele al modelo: «implementa la siguiente feature pendiente».
Paso 3: Fase de Especificación & Puerta Humana
Claude (actuando como leader) invocará al subagente spec_author. Este creará por ejemplo specs/cli_count/ con sus 3 archivos y marcará el status como spec_ready. Claude se detendrá y te dirá:
"Spec listo en specs/cli_count/. Revísalo y di 'aprobado' para continuar con la implementación."
Paso 4: Tu Aprobación Humana
Abre specs/cli_count/requirements.md y design.md. Si estás de acuerdo, escribe en el chat:
Chat Prompt
aprobado
Paso 5: Implementación, Review y Cierre
El leader transiciona a in_progress, lanza al implementer (marca las tasks [x] y añade tests en tests/test_cli.py), y luego al reviewer (audita trazabilidad en progress/review_cli_count.md). Al aprobarse, se marca done en feature_list.json y el resumen pasa a progress/history.md.
